Security model

Bounded by design.

TetherBound is built around a simple rule: connecting an AI assistant to infrastructure should not mean giving it an unrestricted remote shell.

Boundary 01

Network identity

The current Linux path uses a dedicated tagged Tailscale identity with narrowly scoped network and SSH policy.

Boundary 02

Local policy

TetherBound independently filters which hosts, services, log sources, tools, and bounds are allowed. Local policy remains authoritative.

Boundary 03

Typed operations

The MCP surface exposes fixed operations such as disk usage or service status. Caller text does not become a shell command.

What TetherBound deliberately does not provide

  • No generic run_command tool.
  • No unrestricted shell, PTY, PowerShell, WinRM, RDP, or arbitrary script endpoint in the read-only product.
  • No SSH private key stored in ChatGPT or in the current gateway.
  • No public SSH port required for the current Tailscale path.
  • No automatic elevation to root, Administrator, or LocalSystem just to obtain richer telemetry.
  • No silent expansion from one host selector to many targets.
  • No write action inferred directly from remote logs or other untrusted host output.

Native Windows / macOS / Linux read APIs

Windows and mainstream macOS targets are planned around an outbound host agent instead of asking users for reusable passwords or creating a generic remote-command channel. The connector verifies both the Tailscale source identity and the agent certificate before dispatching typed operations.

Cloud does not replace the local boundary

The planned hosted product adds authentication, routing, policy management, health, and audit metadata. The customer edge connector still performs a second authorization decision locally. Hosted policy may narrow local access but is not allowed to widen it.

The planned cloud relay will necessarily carry result data on its way back to the AI client. The default design is to stream that output rather than retain it. Audit records keep metadata such as actor, host, tool, policy decision, duration, byte counts, truncation, and status—not raw process listings or log output by default.

Remote content is untrusted

Hostnames, logs, process arguments, service descriptions, and other machine-derived strings can contain malicious or misleading text. TetherBound treats them as data, bounds their size, strips unsafe terminal control sequences, and avoids feeding remote text directly into future write actions.

Write actions come later

The proposed write model is intentionally different from the read model:

prepare_action
      ↓
resolve host + policy + exact immutable action
      ↓
approve_action
      ↓
short-lived approval bound to that exact action
      ↓
execute_approved_action

Arbitrary shell access remains out of scope. A restart, deployment, cache clear, or similar operation must be implemented as its own typed capability with its own authorization and audit semantics.
